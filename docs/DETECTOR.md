# A learned detector for instruction-carrying telemetry fields

Tiers 1-3 defend the narrator: they change how the LLM is prompted, or how
much of the report the LLM is allowed to author. This asks a different
question. Can a small model look at one attacker-controlled field value - a
process path, a command line, a DNS name, with no surrounding context - and
tell whether it is carrying an instruction, before the narrator ever sees it?

If it can, it is a cheap control that composes with all three tiers. If it
cannot, that is worth knowing too, because "run a classifier over the fields
first" is the reflexive answer to this threat and it should be measured
rather than assumed.

## The failure mode the whole design is built around

Injected field values are longer and more English-like than real ones. A
classifier can score beautifully by learning "long, wordy string" and nothing
else, and every headline metric will look like a working detector.

This is not hypothetical. An earlier interpretability probe I built hit 100%
accuracy at layer 0 of GPT-2 - a layer that has done no computation - because
the two prompt conditions differed in length. The lesson transferred directly:
build the control before the model, and keep running it.

So three things are load-bearing here, and they are all in
[`detector/`](../detector):

**A length-only control.** `LengthOnly` in `classical.py` sees two numbers per
example - character count and token count - and nothing else. It is fitted and
reported on every split, every run. Whatever it scores is the floor. A model
that does not clearly beat it has learned to count characters.

**Hard negatives.** About a third of the benign class is deliberately wordy
and full of the vocabulary an injection uses: `security`, `approved`, `scan`,
`policy`, `false positive`, ticket numbers, whole English clauses. Real
examples, of the shape a real SOC sees constantly:

```
ansible-playbook site.yml --comment "monthly patch cycle, approved change CHG0041882"
/var/log/soc/audit/INC0093441-reviewed-by-tier-2-closed.log
HKLM\SOFTWARE\Policies\Microsoft\Windows Defender\Exclusions\Paths\baseline-CHG0052117
Mozilla/5.0 (compatible; Nessus/10.7) authorized internal vulnerability scan
```

Their false-positive rate is reported separately from the overall one. A
detector that fires on these is unusable no matter what its ROC curve says.

**Held-out techniques.** Attacks are generated by ten named families, and
three of them - `schema_forgery`, `label_naming`, `unicode_evasion` - never
appear in training. They were picked to span three different mechanisms (a
syntactic attack on the response schema, a semantic attack that names the
allow-list, an encoding attack) rather than three variations on one, so
"generalises to unseen techniques" is not quietly measuring "generalises to
unseen wording of a technique it already knows."

## The splits

| split | injections from | benign vocabulary | what it asks |
|---|---|---|---|
| `train` | 7 families | train pool | — |
| `val` | 7 families | **val pool** | where the threshold is fitted |
| `test_seen` | 7 families | test pool | new strings, known techniques |
| `test_unseen` | **3 held-out families** | test pool | a technique never trained on |
| `test_human` | **the 66 hand-written corpus payloads** | test pool | the only split not written by this code |

`test_human` is the number to believe. Those 66 payloads were written by hand
months before this detector existed, for a different purpose, and they are the
only positives in the project that did not come out of the same generator that
produced the training data.

### The benign side had to be rebuilt

The first version listed ~15 realistic benign strings per field and mutated
them lightly. It produced a `char_ngram_lr` baseline scoring **ROC-AUC 1.000
on validation and a 47% false-positive rate on the test split**. It had
memorised the list; fifteen templates cannot be partitioned into disjoint
train and test pools and still describe a distribution.

The rebuild makes benign generation compositional - vendors, products,
directories, tools, flags, hostnames, ticket prefixes - and splits every
component vocabulary three ways. Train, validation and test now draw
structurally similar strings from disjoint words, which is what "the detector
has not seen this benign value before" is supposed to mean. Validation draws
from its own pool too, so the threshold fitted on it is an honest estimate of
what the threshold will do on test rather than a measurement of what the model
memorised.

## Protocol

Fixed before any numbers were looked at:

- Fit on `train` only. Select the checkpoint on `val` **PR-AUC**, not accuracy
  — on a mostly-benign stream, accuracy is maximised by predicting "benign"
  forever.
- Choose one operating threshold per model, on `val`, at a **1% false-positive
  rate**. Apply that same threshold, unchanged, to every test split. Picking a
  per-split threshold that maximises that split's own numbers is how a
  detector gets reported as working when it is not.
- Report the length-only control alongside every model on every split.

1% is already a generous budget. Every telemetry field on every event passes
through this thing, so on a real estate 1% is thousands of alerts a day.

## Models

| model | what it is | why it is here |
|---|---|---|
| `length_only_control` | logistic regression on `[char_count, token_count]` | the floor |
| `char_ngram_lr` | TF-IDF over character 3-5 grams → logistic regression | the cheap baseline that is genuinely hard to beat on short punctuation-heavy strings |
| `distilroberta_base_ft` | fine-tuned sequence classifier, 3 epochs, CPU | the thing being tested |

If the transformer cannot beat the char n-gram baseline, the honest conclusion
is to ship the baseline. It trains in a tenth of a second.

## Running it

```
pip install -e ".[detector]"
python -m detector.dataset        # split sizes and per-class length stats
python -m detector.experiment     # every model, every split -> detector/results/
python -m detector.experiment --fast   # skip the transformer fine-tune
```

Results land in `detector/results/detector_<UTC-timestamp>.json` with every
report, the fitted threshold, and per-family recall.
